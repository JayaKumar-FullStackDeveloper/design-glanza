01Purpose & Vision

Design-Glanza is not a product and not a product builder. Per its own root README.md and master SKILL.md, it is a Product-Builder Skill Factory and Orchestrator — a single, domain-agnostic Claude Code skill whose job is to read a raw product requirement (a BRD/PRD/SOW, user stories, acceptance criteria, an existing product, screenshots, or a plain-language idea) and generate a second, separate, product-specific skill — a Product Builder — that then does the actual designing, building, testing, auditing, and iterating for that one product.

USER REQUIREMENT  →  PRODUCT UNDERSTANDING  →  PRODUCT-SPECIFIC BUILDER  →  COMPLETE PRODUCT
The one sentence that matters most: "Design-Glanza creates and orchestrates Product Builders. Product Builders execute product-specific work." (SKILL.md). Confusing the two is the single most common way to misunderstand this system.

Why this shape, and not a single monolithic skill

  • Domain-agnostic core, domain-specific output. The master engine (methodology, UX/UI technique, rules, gates) never hardcodes a domain — Rule 14. A new domain is added by writing one new product-types/<domain>.md pack, never by editing core reasoning.
  • Product isolation. Everything learned while building one product stays inside that product's generated folder under products/<slug>/ — Rule 15. The master skill never accumulates one customer's business rules.
  • Reasoning before rendering. Rule 1/4: no UI is generated before the problem, users, and business logic are understood. This is enforced structurally (phase-transition gates), not just as an instruction.

Vision, as actually built vs. as originally stated

As of the current on-disk state (version 1.0.9), every folder has real, load-bearing content, one full product has been generated through Prototype (products/projectflow), and the system has been iteratively extended across nine minor versions since 1.0.1 — six passes of external design-knowledge integration, a Domain Standards Library, a mandatory Design Setup / visual-direction phase, a mandatory Preview & Run phase, and (this version) a mandatory design-research-and-visual-audit system. Unlike the earlier baseline of this document, the root README.md is now current and the project is under git version control, published at github.com/JayaKumar-FullStackDeveloper/design-glanza — two of the previously-flagged drift risks are resolved (§19 tracks what still isn't).

A generated Product Builder's own SKILL.md literally states: "Contains product-specific knowledge only; references the master skill... for all reusable methodology." 07How PDFs + domain-registry.json Are Used

Registry schema (verified against the real file)

{
  "id": "DG-001",                 // stable identifier, cited in domain-application-notes.md
  "domain": "Admin Panel",        // human name — the primary matching vocabulary
  "category": "01-core-business", // 1 of 12 top-level folders
  "slug": "admin-panel",          // compared against product-types/*.md filenames
  "path": "01-core-business/001-admin-panel",
  "standard": "complete",         // "complete" | "pending"
  "standard_file": "standard.pdf" // filename, or null when pending
}

The load procedure, exactly as implemented

  1. Score the registry's domain names/synonyms against extracted BRD facts — same signal-strength discipline as domain-classifier.md (a single weak mention never selects an entry).
  2. Single confident match → load it. Multiple genuinely-applicable matches (e.g. a clinic-management product with its own pharmacy module) → load all, tag one primary + rest supporting, recorded with their confidence/signals in product-builder/domain/domain-application-notes.md.
  3. If standard: "complete" — read product-types/domain-standards/<path>/<standard_file> (an actual PDF, via the Read tool) in full. Its content becomes mandatory guidance.
  4. If standard: "pending" (currently 111 of 122 entries) — load nothing. This is explicitly not an error; the system falls through exactly as if the entry didn't exist. Fabricating placeholder guidance for a pending entry is explicitly forbidden (same discipline as Rule 10 for business rules).
  5. Never load an unrelated entry merely for breadth or adjacency.

create-product-builder.py's own stated boundary

Per its docstring: it performs no reasoning. It never invents a business objective, requirement, flow, or rule — it only templates whatever the caller's product definition already contains, marking anything else pending for a later phase/--update to fill in. product_type is discovered dynamically from whatever .md files actually exist in product-types/ — a new pack becomes valid with zero script changes.

11Decision-Making and Routing Logic

Three distinct decision mechanisms, each with a stated scope

MechanismAnswersFile
Rule 2 — Source of Truth"When facts conflict, which one wins?" (8 tiers)config/operating-rules.md

The feedback-routing table (verbatim logic)

Test findingRoutes to
Task completion failureDefine (primary), Ideate if Define still holds
Business-rule incorrectnessDefine + business-logic.md
Usability / discoverability / feedback / responsiveness failurePrototype (execution), rarely Ideate (only if the interaction model itself, not its execution, is the cause)
Accessibility failurePrototype structural, or color-system.md perceptual
Edge case failureEmpathize (never surfaced) or Prototype (surfaced but not designed for)
Escalation, not infinite looping: if the same finding survives more than two Prototype→Test cycles at the same scope, that's a signal the problem is one level up (Ideate's approach or Define's framing) and must escalate there — never keep silently cycling.

Ideate's own decision discipline

Criteria are split into threshold (hard pass/fail — e.g. accessibility-by-construction; a failure here disqualifies before scoring) and trade-off (genuinely weighed). A near-tie between approaches is treated as "a priority problem, not a design problem" and escalated for an explicit priority call rather than resolved by picking the higher score anyway.

14Extensibility for Adding New Domains/Products

Adding a new broad domain (a 13th product-type pack)

  1. Author one new product-types/<domain>.md answering the same fixed 12-point Domain Pack Contract defined in custom-domain.md (characteristics, users, workflows, info structures, nav patterns, UI patterns, operational concerns, edge cases, terminology, UX risks, accessibility, scalability) — citing core files, never restating their technique.
  2. No core file changes. create-product-builder.py discovers the new pack dynamically by scanning product-types/*.md.
  3. Add a signal row to domain-classifier.md's scoring table (optional but recommended, as done for landing-page).

Adding a new fine-grained domain standard (a 123rd registry entry)

  1. Add one JSON object to domain-registry.json (id, domain, category, slug, path, standard, standard_file).
  2. Create the folder at path with either a real standard.pdf ("standard":"complete") or a placeholder README.md ("standard":"pending").
  3. Zero code changes — domain-standards.md's matching procedure reads the registry live.

The graduation rule (turning a recurring "custom" case into a real pack)

When the same domain keeps routing through custom-domain.md's no-match fallback across multiple products, that recurrence is itself the signal to author a proper new pack — never by editing the domain-agnostic core.

Adding a new default design sample (a 14th design-samples/ folder, added v1.0.7)

Same zero-core-change discipline: add a folder under design-samples/ plus a one-line mention in reference-selection.md's selection list — no script change, since Default-mode selection is a direct slug match against the confirmed domain, not a scored classification.

The 21-dimension weighted Evaluation Rubric

Grouped into 3 tiers so visual polish cannot mathematically win: Tier A (Product Reasoning, ×3 weight, 7 dims, 105 pts), Tier B (Workflow Completeness, ×2, now 12 dims — Design direction quality, Preview & run verification, and this version's new Visual benchmark & audit cycle dimension all live here, not in Tier C, 120 pts), Tier C (Visual/Presentation, ×1, 2 dims, 10 pts — capped under 5% of the 235-point total, up from 205 at the v1.0.6 baseline). A flawless design system with weak requirement understanding or broken traceability cannot score well overall.

19Current Architecture Strengths, Gaps, Risks & Improvement Opportunities

Strengths

Strength Genuine separation of reasoning from mechanics. Every script's docstring states, in writing, exactly what it does not judge — the single clearest example being generate-report.py rendering unjudgeable sections as "Not evaluated by this script" instead of fabricating a verdict.
Strength Self-consistent ID/traceability model (REQ→USER→FLOW→SCREEN→COMPONENT→TEST) is enforced by an actual script (validate-product.py), not just described in prose.
Strength Weighted scoring that structurally prevents a "pretty but empty" pass — Tier C (visual) is mathematically capped under 5% of the total, and stayed capped even as the total grew from 205→235 points and gained a whole new visual-audit dimension (B15) that was deliberately placed in Tier B, not Tier C.
Strength Disciplined, justified extensibility. Nine minor versions since 1.0.1 each added real capability without ever inflating the phase count casually — the two phases that were added (Design Setup v1.0.7, Preview & Run v1.0.8) each came with a named rule, a named gate, and a stated reason, taking the lifecycle from 10→12 phases, rules from 17→20, and measurable gates from 12→15 deliberately, not by drift.
Strength The project now practices what its own quality gates preach about honesty. This version's new mandatory visual-audit cycle (B15) requires recording that a check ran even when it found nothing wrong — the same "don't silently skip, don't fabricate a pass" discipline the rest of the toolchain (§13, §16) already lived by is now explicitly extended to visual/UI quality, closing what was previously the one area most exposed to a "looks fine, ship it" shortcut.
