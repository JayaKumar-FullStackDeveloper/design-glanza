01Purpose & Vision

Design-Glanza is not a product and not a product builder. Per its own root README.md and master SKILL.md, it is a Product-Builder Skill Factory and Orchestrator — a single, domain-agnostic Claude Code skill whose job is to read a raw product requirement (a BRD/PRD/SOW, user stories, acceptance criteria, an existing product, screenshots, or a plain-language idea) and generate a second, separate, product-specific skill — a Product Builder — that then does the actual designing, building, testing, auditing, and iterating for that one product.

USER REQUIREMENT  →  PRODUCT UNDERSTANDING  →  PRODUCT-SPECIFIC BUILDER  →  COMPLETE PRODUCT
The one sentence that matters most: "Design-Glanza creates and orchestrates Product Builders. Product Builders execute product-specific work." (SKILL.md). Confusing the two is the single most common way to misunderstand this system.

Why this shape, and not a single monolithic skill

  • Domain-agnostic core, domain-specific output. The master engine (methodology, UX/UI technique, rules, gates) never hardcodes a domain — Rule 14. A new domain is added by writing one new product-types/<domain>.md pack, never by editing core reasoning.
  • Product isolation. Everything learned while building one product stays inside that product's generated folder under products/<slug>/ — Rule 15. The master skill never accumulates one customer's business rules.
  • Reasoning before rendering. Rule 1/4: no UI is generated before the problem, users, and business logic are understood. This is enforced structurally (phase-transition gates), not just as an instruction.

Vision, as actually built vs. as originally stated

As of the current on-disk state (version 1.0.32), every folder has real, load-bearing content. Several products have been generated in the external workspace, including ProjectFlow (through Prototype, §18), OneZae Admin Panel (partial), and two new synthetic benchmark products (figma-validation-demo, figma-validation-demo-fintech) built specifically to exercise the new Figma capability end to end — none of these are tracked in this repository (Rule 15). The system has been iteratively extended across thirty-one minor versions since the v1.0.9 baseline this document originally analyzed. Growth since then spans a Design Research Engine, UX Scenario Testing, Design Token Intelligence, a Component Intelligence Registry, Visual Regression & Comparison, Product Memory/ADRs, nine successive quality-pass hardenings, a real browser-rendering visual-QA layer (Playwright-based, v1.0.28–29), and — newest and largest — Figma designs as a high-fidelity design reference/input (v1.0.30), a strict validation pass on it (v1.0.31), and an automated-conformance/benchmark-driven hardening pass (v1.0.32) — detailed in the new callout above. The root README.md remains current, the project stays under git version control at github.com/JayaKumar-FullStackDeveloper/design-glanza, and the master skill is invokable via the Skill tool directly, not only the explicit /design-glanza command (§9). §19 tracks what still isn't resolved.

The central architectural invariant

A generated Product Builder's own SKILL.md literally states: "Contains product-specific knowledge only; references the master skill... for all reusable methodology." Every technique file is cited by relative link, never duplicated. This is verified in the actual generated file (§18) — it is not just an aspiration.

New since v1.0.29: Figma as a high-fidelity design reference (v1.0.30–v1.0.32)

The single biggest capability addition since this document's last pass. Design-Glanza can now treat an existing Figma design as a high-fidelity design reference/input for a new screen — added alongside, never in place of, sample images, written guidelines, and the engine's own default standards. It adds zero new lifecycle phases, agents, gates, or pipeline rows; it lives entirely inside the existing Design Setup phase and the existing Reference-Driven classification mode.
  • Where it lives: design-reference-engine/figma-reference.md (the extraction technique — structured inspection where a Figma file's own structure is actually readable, falling back to the engine's existing image-only technique otherwise, with the fallback always explicitly recorded, never silent) and figma-context-consumption.md (the precedence rule: prefer a genuine Figma-matched token/component/pattern; where none exists, use the existing Design-Glanza default kept consistent with the extracted Figma language). The normalized output is figma-context.schema.json-shaped — a figma-context.json written to BRD/figma/ per product.
  • The one tool-surface exception: SKILL.md's allowed-tools gained a narrowly-scoped grant — the figma-use/figma-design-to-code skills and their use_figma/get_design_context tools, read-only, invoked only inside Design Setup when a Figma reference is actually detected. No other network/MCP tool was added; the skill's "no general shell access" posture otherwise holds exactly as before.
  • Two injection points, both inside Design Setup, confirmed by direct diff: workflows/execute-product-builder.md's action rows 15 ("detect and analyze design references") and 18 ("write the complete Design Direction") each gained one clause citing the Figma technique — no row added, removed, or reordered; every other row's text is byte-identical to v1.0.29.
  • Two-level Visual QA (v1.0.30, automated v1.0.32): Level A is the existing reference-image similarity check (compare-reference-visual.py), now explicitly supporting a Figma-exported frame as the reference asset. Level B is new — Figma-spec conformance: does the generated screen's actually-rendered color/radius/typography/spacing match the Figma Design Context's own token values? v1.0.30/31 specified this as a manual, agent-by-hand comparison; v1.0.32 automated it with a new deterministic script, scripts/validate-figma-conformance.py (two checks: does a token citing a Figma source actually trace to a real entry, and was that value ever actually rendered). Both levels feed the existing B15/B20 gates as new gap-type rows — no new gate number was created.
  • Verified by a real (synthetic-fixture) benchmark, not by prose alone: three test cases — a simple new screen, a complex multi-step workflow screen, and a new screen against a second, deliberately different Figma design language (dark/dense fintech vs. the first's light SaaS register) — were actually run through capture-render.py/validate-rendered-layout.py/compare-reference-visual.py/validate-figma-conformance.py. Real defects were found and fixed in the process: a responsive overflow bug in the complex screen (fixed with a new reusable component-registry/composition-patterns.md organism, "Inline Control Row"), and — while building the automation in fix (1) above — three real bugs in the checking mechanism itself (capture-render.py originally captured no computed style at all, then missed borderColor/padding/gap; a first-draft citation-detection regex matched any bare mention of "Figma" in a token's description, producing both false positives and negatives, fixed by specifying a precise literal marker in design-tokens/token-schema.md; a CSS-quoted vs. plain-string font-family comparison bug).
Not yet verified: live, OAuth-authenticated Figma access has never been exercised in this environment — the Figma MCP connection requires a user-completed authorization flow that has not happened here, so every test above used a clearly-labeled synthetic Figma Design Context, not a real pulled file. The mechanism's own degrade-on-failure path (recording an explicit fallback rather than failing silently) is real and was tested; a live end-to-end run against an actual Figma file remains open (§19).

The load procedure, exactly as implemented

  1. Score the registry's domain names/synonyms against extracted BRD facts — same signal-strength discipline as domain-classifier.md (a single weak mention never selects an entry).
  2. Single confident match → load it. Multiple genuinely-applicable matches (e.g. a clinic-management product with its own pharmacy module) → load all, tag one primary + rest supporting, recorded with their confidence/signals in product-builder/domain/domain-application-notes.md.
  3. If standard: "complete" — read product-types/domain-standards/<path>/<standard_file> (an actual PDF, via the Read tool) in full. Its content becomes mandatory guidance.
  4. If standard: "pending" (currently 111 of 122 entries) — load nothing. This is explicitly not an error; the system falls through exactly as if the entry didn't exist. Fabricating placeholder guidance for a pending entry is explicitly forbidden (same discipline as Rule 10 for business rules).
  5. Never load an unrelated entry merely for breadth or adjacency.

14Extensibility for Adding New Domains/Products

Adding a new broad domain (a 13th product-type pack)

  3. Add a signal row to domain-classifier.md's scoring table (optional but recommended, as done for landing-page).

  1. Add one JSON object to domain-registry.json (id, domain, category, slug, path, standard, standard_file).
  2. Create the folder at path with either a real standard.pdf ("standard":"complete") or a placeholder README.md ("standard":"pending").

The graduation rule (turning a recurring "custom" case into a real pack)

When the same domain keeps routing through custom-domain.md's no-match fallback across multiple products, that recurrence is itself the signal to author a proper new pack — never by editing the domain-agnostic core.

Adding a new default design sample (a 14th design-samples/ folder, added v1.0.7)
