01Purpose & Vision

Design-Glanza is not a product and not a product builder. Per its own root README.md and master SKILL.md, it is a Product-Builder Skill Factory and Orchestrator — a single, domain-agnostic Claude Code skill whose job is to read a raw product requirement (a BRD/PRD/SOW, user stories, acceptance criteria, an existing product, screenshots, or a plain-language idea) and generate a second, separate, product-specific skill — a Product Builder — that then does the actual designing, building, testing, auditing, and iterating for that one product.

USER REQUIREMENT  →  PRODUCT UNDERSTANDING  →  PRODUCT-SPECIFIC BUILDER  →  COMPLETE PRODUCT
The one sentence that matters most: "Design-Glanza creates and orchestrates Product Builders. Product Builders execute product-specific work." (SKILL.md). Confusing the two is the single most common way to misunderstand this system.

Why this shape, and not a single monolithic skill

  • Domain-agnostic core, domain-specific output. The master engine (methodology, UX/UI technique, rules, gates) never hardcodes a domain — Rule 14. A new domain is added by writing one new product-types/<domain>.md pack, never by editing core reasoning.
  • Product isolation. Everything learned while building one product stays inside that product's generated folder under products/<slug>/ — Rule 15. The master skill never accumulates one customer's business rules.
  • Reasoning before rendering. Rule 1/4: no UI is generated before the problem, users, and business logic are understood. This is enforced structurally (phase-transition gates), not just as an instruction.

Vision, as actually built vs. as originally stated

The root README.md still describes the project as "Architecture shell only" with phase logic "not implemented yet." That description is stale — as of the current on-disk state (version 1.0.6), every folder has real, load-bearing content, one full product has been generated end-to-end through Prototype (products/projectflow), and the system has been iteratively extended six times with external design knowledge and a Domain Standards Library. This drift between the stated vision and the actual state is tracked in §19.

02Overall Architecture

Design-Glanza is organized as four layers, each with a distinct authority and lifespan:

LayerLocationLifespanContains
1. Master Skill.claude/skills/design-glanza/Permanent, versioned (currently 1.0.6)The domain-agnostic reasoning engine: rules, gates, methodology, UX/UI technique, agents, workflows, templates, scripts, evals
2. Domain Overlaysproduct-types/*.md + product-types/domain-standards/Permanent, extended over time12 authored domain packs (Domain Pack Contract) and a 122-entry externally-sourced UI/UX standards registry — two independent, composable domain-matching systems
3. Portable Plugindesign-glanza-plugin/Snapshot, manually syncedA Claude Code plugin-packaged mirror of the master skill, for distribution outside this one project

The central architectural invariant

A generated Product Builder's own SKILL.md literally states: "Contains product-specific knowledge only; references the master skill... for all reusable methodology." Every technique file is cited by relative link, never duplicated. This is verified in the actual generated file (§18) — it is not just an aspiration.

07How PDFs + domain-registry.json Are Used

Registry schema (verified against the real file)

{
  "id": "DG-001",                 // stable identifier, cited in domain-application-notes.md
  "domain": "Admin Panel",        // human name — the primary matching vocabulary
  "category": "01-core-business", // 1 of 12 top-level folders
  "slug": "admin-panel",          // compared against product-types/*.md filenames
  "path": "01-core-business/001-admin-panel",
  "standard": "complete",         // "complete" | "pending"
  "standard_file": "standard.pdf" // filename, or null when pending
}

The load procedure, exactly as implemented

  1. Score the registry's domain names/synonyms against extracted BRD facts — same signal-strength discipline as domain-classifier.md (a single weak mention never selects an entry).
  2. Single confident match → load it. Multiple genuinely-applicable matches (e.g. a clinic-management product with its own pharmacy module) → load all, tag one primary + rest supporting, recorded with their confidence/signals in product-builder/domain/domain-application-notes.md.
  3. If standard: "complete" — read product-types/domain-standards/<path>/<standard_file> (an actual PDF, via the Read tool) in full. Its content becomes mandatory guidance.
  4. If standard: "pending" (currently 111 of 122 entries) — load nothing. This is explicitly not an error; the system falls through exactly as if the entry didn't exist. Fabricating placeholder guidance for a pending entry is explicitly forbidden (same discipline as Rule 10 for business rules).
  5. Never load an unrelated entry merely for breadth or adjacency.

Where a loaded standard actually gets applied

ConcernConsuming agent

No ux-engine/* or ui-engine/* core file is ever edited to accommodate a domain standard — Rule 14 applies to this library exactly as it applies to product-types/*.md. The standard is consumed at the agent layer, which is architecturally where domain-specific and domain-agnostic content are designed to combine.

11Decision-Making and Routing Logic

Three distinct decision mechanisms, each with a stated scope

MechanismAnswersFile
Rule 2 — Source of Truth"When facts conflict, which one wins?" (8 tiers)config/operating-rules.md
Design Judgment Engine"Which UI/UX pattern, for an important decision with no more specific owning file?" — 9 steps × 12 weighing factors + an anti-fashion strip-away testmethodology/design-judgment.md
Feedback-Routing Table"A Test finding failed — which phase actually owns the fix?"methodology/design-thinking.md

The feedback-routing table (verbatim logic)

Test findingRoutes to
Task completion failureDefine (primary), Ideate if Define still holds
Business-rule incorrectnessDefine + business-logic.md
Usability / discoverability / feedback / responsiveness failurePrototype (execution), rarely Ideate (only if the interaction model itself, not its execution, is the cause)
Accessibility failurePrototype structural, or color-system.md perceptual
Edge case failureEmpathize (never surfaced) or Prototype (surfaced but not designed for)
Escalation, not infinite looping: if the same finding survives more than two Prototype→Test cycles at the same scope, that's a signal the problem is one level up (Ideate's approach or Define's framing) and must escalate there — never keep silently cycling.

Ideate's own decision discipline

Criteria are split into threshold (hard pass/fail — e.g. accessibility-by-construction; a failure here disqualifies before scoring) and trade-off (genuinely weighed). A near-tie between approaches is treated as "a priority problem, not a design problem" and escalated for an explicit priority call rather than resolved by picking the higher score anyway.

13Automation Opportunities

  • create-product-builder.py — scaffolding, conflict guard, content-preserving --update

14Extensibility for Adding New Domains/Products

Adding a new broad domain (a 13th product-type pack)

  1. Author one new product-types/<domain>.md answering the same fixed 12-point Domain Pack Contract defined in custom-domain.md (characteristics, users, workflows, info structures, nav patterns, UI patterns, operational concerns, edge cases, terminology, UX risks, accessibility, scalability) — citing core files, never restating their technique.
  2. No core file changes. create-product-builder.py discovers the new pack dynamically by scanning product-types/*.md.
  3. Add a signal row to domain-classifier.md's scoring table (optional but recommended, as done for landing-page).

Adding a new fine-grained domain standard (a 123rd registry entry)

  1. Add one JSON object to domain-registry.json (id, domain, category, slug, path, standard, standard_file).
  2. Create the folder at path with either a real standard.pdf ("standard":"complete") or a placeholder README.md ("standard":"pending").
  3. Zero code changes — domain-standards.md's matching procedure reads the registry live.

The graduation rule (turning a recurring "custom" case into a real pack)

When the same domain keeps routing through custom-domain.md's no-match fallback across multiple products, that recurrence is itself the signal to author a proper new pack — never by editing the domain-agnostic core.

15Quality Gates and Validation

Section A — 10 phase-transition gates

config/quality-gates.md gates every phase boundary (Intake→Empathize, ..., Audit→Iterate). The 18-dimension weighted Evaluation Rubric

Grouped into 3 tiers so visual polish cannot mathematically win: Tier A (Product Reasoning, ×3 weight, 7 dims), Tier B (Workflow Completeness, ×2, 9 dims), Tier C (Visual/Presentation, ×1, 2 dims — capped under 5% of the 205-point total). A flawless design system with weak requirement understanding or broken traceability cannot score well overall.

Scope actually completed

Concrete artifacts produced

  • Roles: ROLE-001 Owner, ROLE-002 Project Manager, ROLE-003 Team Member, ROLE-004 Guest/Viewer, plus SYSTEM

  • Dependency graph: Workspace & Membership → Projects → Tasks → {Notifications, Reporting}; confirmed acyclic; DEP-005 (notification delivery) flagged highest-risk assumption
  • Flows: FLOW-001..004 (workspace creation, assign/track task, team-member status update [highest frequency], guest read-only view)
  • IA: Dashboard, Projects (list→Board/List→Task drawer), Workspace Settings (Members, Billing), Notifications, permission-scoped Shared Project node for Guests
  • Navigation: Top nav chosen over sidebar (only 4 top-level sections — doesn't meet the sidebar threshold); breadcrumbs used only at Task Detail, where all 3 conditions are actually met
  • Design system: reuses engine default tokens as-is; zero drift; semantic color mapping applied to task status
  • States: all 13 mandatory states mapped for Dashboard/Board/List/Task Detail/Task Card with zero blank cells; 4 remaining screens flagged as a genuine, disclosed gap — not hidden

19Current Architecture Strengths, Gaps, Risks & Improvement Opportunities

Strengths

Strength Genuine separation of reasoning from mechanics. Every script's docstring states, in writing, exactly what it does not judge — the single clearest example being generate-report.py rendering unjudgeable sections as "Not evaluated by this script" instead of fabricating a verdict.
Strength Self-consistent ID/traceability model (REQ→USER→FLOW→SCREEN→COMPONENT→TEST) is enforced by an actual script (validate-product.py), not just described in prose.
Strength Weighted scoring that structurally prevents a "pretty but empty" pass — Tier C (visual) is mathematically capped under 5% of 205 points.
Strength Disciplined extensibility — six major knowledge-integration passes (v1.0.4–1.0.6) each added real capability without ever inflating the phase count (10), and rule/gate additions were deliberately rare and justified (17 rules, 12 gates, unchanged since the project's early versions except one rule addition).

Gaps & Risks — verified, not speculative

Risk Plugin has drifted materially from the master skill. Confirmed by direct file comparison: the plugin is missing ux-writing.md, localization.md, search-ux.md (ux-engine), craft-critique.md (ui-engine), domain-standards.md (product-intelligence), landing-page.md (product-types), and the entire product-types/domain-standards/ folder + registry. plugin.json's own description text still lists only the original 9 domains with no mention of domain standards or landing pages. There is no sync mechanism — every future master-skill change will widen this gap unless corrected manually.
Risk Generated product manifests silently go stale. products/projectflow/product.json stamps master_skill_version: "1.0.2" — five versions behind the live skill (1.0.6) — with nothing that re-checks or flags this on subsequent reads.
Risk Domain Standards Library is 91% unpopulated. 111 of 122 registry entries are "pending" with only a placeholder README — the mechanism is fully wired and correct, but its actual coverage today is limited to the 11 core-business domains.
Risk Root README.md is stale and actively misleading — it still describes the project as an unimplemented "architecture shell," which was true at v0.1.0 and has not been true since v0.2.0.
Risk No git repository. Confirmed directly — the project has no version control at all; every historical fact lives only in master-config.md's prose changelog. There is no way to diff, branch, revert, or run CI against this project as it stands.
Risk Zero automated tests for the toolchain itself. The changelog records that each validator script was manually verified once, by deliberately constructing bad test content and confirming detection, then deleting the test artifacts — there is no persisted regression-test suite for scripts/*.py.
Risk The eval suite is documentation, not an executable harness. evals/test-cases.md's 10 benchmark scenarios and benchmark-matrix.md's tracking structure exist as markdown specs — nothing currently runs them against a live model automatically.
Risk Single real product, and it stops at Prototype. The entire pipeline's Implement/Test/Audit/Iterate phases have never actually been exercised end-to-end on a real product — ProjectFlow is a genuine, honestly-reported proof of Intake→Prototype only.
Risk A few historical changelog entries carry deliberately-uncorrected stale references (e.g., some 1.0.1-and-earlier changelog text still says "12 mandatory states" after the count became 13) — individually low-risk and explicitly disclosed at the time, but worth knowing before trusting a changelog entry's exact numbers over the live file.

Improvement opportunities (summary — detailed in §20)

  • Initialize git; this single change unlocks diffing, CI, and safe rollback for everything else below.
  • A small sync/drift-detector script between master and plugin.
  • A staleness check on product.json's master_skill_version.
  • An executable eval harness, even a minimal one, for evals/test-cases.md.
  • Complete or actively track the remaining 111 domain standards.
  • Refresh the root README.md to match actual, current capability.

20Recommended Future Architecture

These recommendations are scoped to closing verified gaps above, not a redesign — the core architecture (domain-agnostic engine → domain overlays → generated builders) is sound and should not change shape.

Near-term (low effort, high value)

  1. Initialize version control. Everything else on this list benefits from being diffable and revertible.
  2. Refresh README.md to reflect the actual current state (a one-file, low-risk fix for the single most misleading artifact in the repo).
  3. A scripts/check-plugin-sync.py that diffs file lists (and ideally content hashes) between .claude/skills/design-glanza/ and design-glanza-plugin/skills/design-glanza/, reporting exactly what's missing — turning today's silent drift into a visible, actionable list.
  4. A master_skill_version staleness check inside create-product-builder.py --update: compare the manifest's stamped version against the live master-config.md version and surface a warning (never auto-upgrade silently — that would violate Rule 15/product isolation).

Medium-term

  1. A minimal executable eval runner that walks evals/test-cases.md's 10 scenarios against a live invocation and records results into benchmark-matrix.md's existing schema — turning the Failure Log from a manual, occasional exercise into a repeatable one.
  2. A domain-standards completion tracker — a small script reading domain-registry.json and reporting complete/pending counts per category, to make the 111-pending backlog visible and prioritizable rather than only discoverable by reading the JSON directly.
  3. Run the pipeline through Implement→Iterate at least once on a real or realistic product, specifically to pressure-test the phases that currently exist only as untested prose (build-sequencing, the audit aggregation, the Iterate routing loop in practice).

Explicitly not recommended

  • Do not merge the two domain-matching registries (12 packs vs. 122 standards) into one — they answer genuinely different questions at different granularity, and the current composition (cite, don't replace) is the correct relationship.
  • Do not add a 13th quality gate for "domain standard applied correctly" — the existing agents' input citations and Rule 17's confidence-reporting requirement already cover this without inflating the gate count.
  • Do not auto-regenerate a Product Builder's product.json version stamp on every master-skill change — that would silently rewrite a product's own historical record, violating the same "don't rewrite history" discipline the master changelog itself already follows.
